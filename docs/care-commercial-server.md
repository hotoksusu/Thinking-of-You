# 상용화 서버 운영 안내 — 2026-10-26

운영 Site 버전 91에는 신규 서버가 아직 반영되지 않았다. 자동 승인 검토가 원격 쓰기 자격증명 전달을 거절해 소스 동기화·마이그레이션·배포를 보류했다. 실제 D1·ChatGPT 로그인 경계·문자 발송은 미검증이다.

## 배포·온보딩

Next 정적 export + 단일 ESM Worker, 기존 Sites 프로젝트 ID와 공개 범위 유지, D1 논리 바인딩 `DB`. `prepare-sites-dist.mjs`가 상태규칙·SMS·업무·환자 API를 묶는다. 환자·기관 seed 없음.

1. 운영 리소스·실제 데이터 여부·마지막 정상 배포·백업과 복구 권한을 먼저 확인한다. [파일럿 운영 초안](care-pilot-operations.md)의 롤백 게이트를 충족한다.
2. `CARE_PUBLIC_ORIGIN`을 실제 Site origin으로 설정, `CARE_ADMIN_EMAIL`을 승인된 플랫폼 운영자 이메일로 서버 비밀값에 설정한다. 키 값을 소스·브라우저에 넣지 않는다.
3. `0000_care_server`, `0001_care_operations`, `0002_care_sms`를 저널 순서로 적용한다. 기존 데이터가 있으면 별도 DB 리허설·백업 후 적용한다. 자료 삭제·자동 seed 없음.
4. 플랫폼 운영자가 병원 메타데이터와 승인된 병원 관리자를 등록한다. 운영자 본인의 최초 임상 권한 직접 부여는 차단된다. 환자 접근이 필요하면 병원 관리자가 별도 승인·기간 설정 후 부여하고 사용 후 회수한다.
5. 병원 관리자가 직원 역할·계정 만료일·담당 환자·기록 확인 운영시간·관리기간·의료진 승인 근거를 설정한다. 간호사·직원은 배정 환자, 의사는 소속 허용 환자, 병원 관리자는 소속 운영/보고서에 접근한다.
6. 적법한 수집·민감정보 처리 근거를 확인한 환자만 등록한다. 기존 기기 자료는 내용과 권한을 확인한 뒤 한 환자씩 복사하며 원본은 보존한다. 로컬 역할의 서버 승격이나 전체 업무 자동 이관은 없다.
7. 환자 안내 링크는 내용을 확인해 직접 전달한다. 재발급하면 이전 링크·관련 세션을 폐기한다. **병원 업무 문자 알림과 환자 초대 자동 문자는 별개다. 환자 초대 자동 문자 발송은 미구현이다.**

## 접근·데이터 신뢰성

- 환자 토큰은 256비트 난수·SHA-256 해시 저장, 초대 7일, 세션 30일 절대 만료·14일 미사용 만료. 명시적 확인 후 HttpOnly/Secure/SameSite=Lax 쿠키. GET 봇 방문은 연결을 소비하지 않으며 연결 전 이름을 반환하지 않는다.
- 직원은 플랫폼 인증 헤더와 활성 소속·역할·계정 만료·담당 배정을 매 요청 검증한다. 권한 회수는 다음 API부터 적용된다. 이미 표시된 정보를 원격 삭제할 수 없으므로 공용 PC 잠금·로그아웃도 필요하다. MFA와 플랫폼 로그인 제한은 공급자 설정 검토가 남았다.
- 쓰기는 Origin 검사·최대 100KB 스트리밍 JSON·prepared SQL. 민감 응답 no-store, 페이지 no-referrer/nosniff. 분당 요청 제한은 직원 240, 일반 120. 플랫폼 사용자 ID/신뢰 프록시 IP 해시를 사용하며 IP가 없으면 보수적 공용 익명 버킷. WAF를 대체하지 않는다.
- 기록은 환자+병원+서울 날짜 유일, 수정은 updatedAt 비교. 기록·분류 이유/시각/규칙 버전·확인 신호·알림 대기열·감사를 batch로 저장한다. 업무는 revision·이벤트 ID 중복 방지·이력 저장을 적용한다. 새 응답/수정은 이전 확인과 구분한다.
- 감사에는 이름·연락처·증상·원문 토큰을 남기지 않는다. 조건부 작업의 `attempted` 감사는 실제 이벤트와 함께 확인한다. 플랫폼 URL 로그의 토큰 마스킹은 별도 확인이 필요하다.
- 기존 병원·관리자 로컬 기능을 유지하되 운영 로그인은 실제 서버 로그인으로 안내한다. 데모 비밀번호 입력은 개발 환경에만 표시한다. 기존 로컬 데이터가 서버의 상용 데이터라고 오인되지 않도록 구분한다.

## SOLAPI 병원 업무 알림

사용자의 새 알림 연동 요청에 따라 구현했다. 실제 발송은 아직 하지 않았다. 계정·위탁계약·인증 발신번호·충전/한도·수신번호 승인을 마친 뒤 활성화한다.

서버 비밀값 `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`; 설정 `CARE_SMS_FROM`, `CARE_SMS_ENABLED=true`, `CARE_SMS_DAILY_LIMIT`(기본 50, 최대 1000). 병원 관리자가 알림 설정에서 업무 수신번호·권한을 확인한다. 키가 없어도 환자 기록은 저장되고 미발송으로 표시한다. 운영키를 채팅으로 보내지 않는다.

전송 내용은 업무 확인 안내 고정 문구뿐이다. 환자 이름·진단·증상·환자 ID·초대 토큰을 포함하지 않는다. 제공자는 담당자 번호·발신번호·고정 문구를 처리하므로 해당 처리관계·보관정책은 계약 검토 대상이다.

저장 후 Worker waitUntil에서 시도한다. DB claim과 일일 응답 이벤트키로 중복을 막으며 발송 실패가 기록 저장 성공을 취소하지 않는다. 명확한 실패는 지수 대기 후 최대 3회 수동 재시도. 제공자 접수·단말 전달·의료진 확인은 구분한다. 네트워크 중단처럼 접수 여부가 불명확하면 `unknown`으로 잠그고 재전송을 차단한다. 직접 연락과 제공자 콘솔 확인으로 대응한다. 정기 자동 재시도·전달 조회 스케줄러는 아직 연결하지 않았다.

근거: [HMAC 인증](https://solapi.com/developers/api/authentication-api-key), [발송](https://solapi.com/developers/api/messages), [조회](https://solapi.com/developers/api/msg-getList), [상태 코드](https://solapi.com/developers/api/msgstatus). 접수 2000과 전달 4000을 구분한다. 실제 요금·한도·잔액·발신번호 승인·기관별 발송 계정 분리는 계약 시 확인한다.

## API와 성과

환자 `/api/care/`: invitation, connect, disconnect, state, checkins. 직원 `/api/care/staff/`: state, hospitals, members, patients, invitations, work, policy, care-status, time, report, notification-policy, notifications, audit, security, pilots. 공개 병원 상담 접수는 `POST /api/care/pilot`이며 환자정보 입력용이 아니다.

보고서: 병원 관리자만 기간·월간 조회/CSV, 기준시각·표본·산식·전월 동기간 표시. 활성화는 서버 연결 세션이 있는 대상자, 7/14일차는 퇴원일을 1일차로 해당 날짜에 도달한 표본, 참여율은 관리 예정일수 기준. 확인·후속 처리시간은 실제 이벤트 시각. 업무시간은 실측 일평균을 비교하며 환자군·업무량 차이는 자동 보정하지 않는다. 월간 절감액·임상성과를 임의 계산하지 않는다.

실제 D1·SSO·SMS·백업 복구·MFA·보존/삭제 실행·위탁/의료규제 계약·침투 테스트·실기기 접근성은 운영 전 검증/결정이 남았다. 빌드나 합성 테스트 통과만으로 유료 운영 준비 완료를 선언하지 않는다.
