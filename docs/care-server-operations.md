# 서버 연계 회복 기록 운영 안내 — 이전 구현 기록

**2026-10-26 이후 최신 운영 기준은 [상용화 서버 안내](care-commercial-server.md)와 [파일럿 운영 초안](care-pilot-operations.md)을 따른다. 아래는 이전 서버 구현 당시의 기록이며, ‘후속조치 미연동’, ‘역할 관리 미구현’, ‘자동 문자 없음’ 등은 최신 변경을 반영하지 않는다. 운영 배포가 아직 보류된 상태라는 점은 유지된다.**

## 현재 상태
코드와 로컬 DB/브라우저 통합 검증은 완료. 호스팅 DB 적용과 운영 배포는 자동 승인 검토가 새 수정본의 게시 승인을 요구하여 보류됨. 현재 운영 사이트 버전 91에는 새 서버 API가 아직 없음.

## 배포 구성
- 기존 Sites 프로젝트 및 공개 범위 유지.
- `.openai/hosting.json`: 논리 D1 바인딩 `DB` 추가.
- `drizzle/0000_care_server.sql`, `drizzle/meta/_journal.json`: 신규 테이블만 생성. 실제 환자·병원·샘플 데이터 seed 없음.
- `server/worker.mjs`: 정적 자산 라우팅을 유지하면서 `/api/care/**`를 처리.
- `server/care-api.mjs`: D1 prepared statements와 batch transaction 사용.
- `scripts/prepare-sites-dist.mjs`: 기존 정적 출력과 소스 Worker/서버 API, 기존 상태 평가 규칙을 `dist`로 복사·컴파일.
- `CARE_PUBLIC_ORIGIN`: 배포 전에 현재 운영 사이트 URL의 origin으로 설정. 프록시 내부 주소와 무관하게 Origin 검사와 발급 링크를 공개 도메인으로 고정.
- `CARE_ADMIN_EMAIL`: 사이트 소유자 ChatGPT 로그인 이메일을 서버 환경 비밀값으로 설정. 현재 이 키의 설정은 완료됐으며, 값은 소스/브라우저에 포함하지 않음.

## 첫 운영 설정
1. 승인 후 CARE_PUBLIC_ORIGIN을 현재 Sites 공개 origin으로 설정하고, 같은 프로젝트에 소스 푸시·패키지 저장·DB 마이그레이션·배포.
2. `/care/server`에서 사이트 소유자 계정으로 ChatGPT 로그인. 플랫폼이 검증한 사용자 ID·이메일만 서버에서 사용.
3. 실제 병원 정보를 직접 등록. 테스트 병원/환자는 자동 생성되지 않음.
4. 해당 병원의 실제 담당자 이메일 접근 권한을 등록. 기존 로컬 병원/관리자 계정은 새 서버 쓰기 권한으로 사용하지 않음.
5. 실제 환자를 확인·등록하거나, 이 기기에 있는 기존 자료를 명시적으로 확인한 뒤 한 환자씩 복사. 원본은 삭제하지 않음. 같은 원본을 같은 병원으로 반복 복사해도 중복 생성하지 않도록 참조키 사용. 이미 가져온 원본은 기존 서버 환자를 반환하며 이후 기기 수정 내용을 자동으로 합치지 않음.
6. 환자별 서버 안내 링크를 발급하고, 내용을 확인해 직접 복사·전달. 자동 문자/카카오톡 발송 기능 없음.
7. 환자가 링크를 열어 본인 안내임을 확인하면 서버 세션이 연결됨. 오늘 기록은 서버 저장 응답을 받은 뒤에만 완료 표시.

## 인증·저장 경계
- 공개 회원가입 없음. 기관/환자 등록은 서버에서 허용된 병원 계정만 가능.
- 초대 토큰과 환자 세션은 암호학적 난수이며 DB에는 SHA-256 해시만 저장.
- 세션 쿠키: `__Host-care_session`, HttpOnly, Secure, SameSite=Lax, Path=/.
- 초대 유효기간 7일, 세션 30일. 기존 구현과 같은 범위이며 편의를 위해 임의 연장하지 않음.
- 초대 취소 시 해당 초대로 만들어진 세션 접근도 차단.
- 모든 쓰기 요청은 같은 Origin인지 확인. 서버가 세션의 환자·병원을 선택하며 클라이언트의 ID/역할은 권한으로 사용하지 않음.
- 병원 담당자는 허용된 병원 범위만 조회·등록·발급 가능. 사이트 운영자만 담당자 접근 권한과 병원을 등록.
- 당일 기록은 환자+병원+서울 날짜로 유일. POST 중복은 기존 기록 반환. PUT은 기존 수정 시각이 일치해야 하며 충돌 시 409.
- 기록과 기존 파일럿 규칙의 확인 신호는 한 DB batch로 처리. 저장 실패 시 완료 표시 없음.
- 관리기간이 종료된 서버 환자는 읽기 화면을 제공하고 신규 기록 쓰기를 거절.
- 실제 상태 평가는 기존 `src/lib/status-rules.ts`를 재사용. 새 진단/응급 분류 알고리즘을 만들지 않음. 기존 규칙은 파일럿 업무 보조용이며 의료 진단으로 표시하지 않음.
- 환자/초대/서버 병원 관리 화면에서 사용하지 않는 외부 Kakao 공유 SDK를 로드하지 않음. 기존 가족 공유 화면의 기능은 유지.

## 기존 기기 자료와의 관계
- 기존 초대와 로컬 기록의 인증/저장 경로를 보존. 서버에서 검증되지 않은 로컬 세션을 서버 권한으로 교환하지 않음.
- 기존 기록 화면은 ‘이 기기에 저장’으로 표시. 서버에 전송됐다는 문구를 사용하지 않음.
- 새 `srv_…` 안내 링크만 새 서버 초대 검증에 사용.
- 서버 연결 후 기존 기기 링크로 돌아갈 때 해당 브라우저의 서버 쿠키를 해제해 환자 혼선을 방지. 기존 기기 자료는 그대로 보존.
- 기존 병원 대시보드의 로컬 업무/보고서 기능은 유지. 새 서버 환자의 조회·링크 관리·리포트는 `/care/server`에서 제공.
- 기존 병원의 모든 후속 조치/배정/운영 분석을 자동으로 서버로 옮기지는 않음. 이번 신규 백엔드는 환자 등록·링크·세션·회복 기록과 병원별 조회 중심.

## API
| API | 인증/기능 |
|---|---|
| POST `/api/care/invitation` | 서버 초대 유효성 및 최소 본인 확인 안내 |
| POST `/api/care/connect` | 유효 초대와 확인 후 보안 쿠키 발급 |
| POST `/api/care/disconnect` | 현재 브라우저 서버 세션 해제 |
| GET `/api/care/state` | 세션의 환자/병원/기록만 조회 |
| POST `/api/care/checkins` | 실제 당일 기록 생성, 중복 방지 |
| PUT `/api/care/checkins` | 당일 수정, 수정 시각 충돌 검사 |
| GET `/api/care/staff/state` | 승인된 병원 범위의 서버 자료 조회 |
| POST `/api/care/staff/hospitals` | 사이트 운영자의 실제 병원 등록 |
| POST `/api/care/staff/members` | 사이트 운영자의 병원 담당자 권한 등록 |
| POST `/api/care/staff/patients` | 권한 병원의 실제 환자 등록/선택적 기존 자료 복사 |
| POST `/api/care/staff/invitations` | 권한 병원의 환자 링크 발급 |
| DELETE `/api/care/staff/invitations` | 링크 및 연계 세션 접근 취소 |

## 미검증/추가 개발
- 호스팅 D1 마이그레이션과 실제 ChatGPT 로그인/운영 DB 저장은 배포 후 확인 필요.
- 테스트는 실제 서버 API 코드와 SQLite/D1 호환 어댑터를 사용. 운영 환자의 정보를 테스트에 사용하지 않음.
- 내부 직원별 더 세밀한 역할 권한, 구성원 제거 UI, 병원 후속 조치의 서버 이관, 데이터 보관/삭제·백업 정책 및 운영 감사 체계는 후속 항목.
- 개인정보 처리방침과 병원별 동의·계약 문구의 운영 검토는 필요. 코드 테스트만으로 법적 준수를 보장하지 않음.
