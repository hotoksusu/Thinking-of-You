# 다녀온 보안 및 데이터 흐름

## 데이터 경로

1. 병원 관리자 로그인 → Sites 신뢰 경계의 사용자 ID·이메일 → Worker의 활성 직원 소속·역할 조회 → D1의 병원·환자 등록과 링크 발급.
2. 환자 전용 링크 → 만료 및 폐기 검사 → 본인 링크 이용 확인 → HttpOnly·Secure·SameSite 세션 → 서버에서 연결된 환자 한 명의 기록만 조회·저장. 링크와 세션 원문은 해시화하며 복사 링크에는 원문이 들어가므로 승인된 경로로만 전달한다.
3. 체크인 저장 → 환자·병원·일자별 중복 제한 → 병원의 업무 목록 → 확인·조치·후속 상태 및 작성자·작성시각 저장 → 병원 관리자 리포트와 감사 로그.
4. 병원 도입 문의 → 담당자 정보·고정 선택지·동의 버전을 별도 저장 → 플랫폼 운영자 조회. 환자 정보 필드를 접수하지 않는다.
5. 등록된 업무 알림 → 발송 설정과 병원 권한·정책 확인 → 발송권 획득 → 제공자 접수·전달 상태 기록. 내용에는 환자 이름과 건강정보를 포함하지 않는다. 데모에서는 제공자 기능을 비활성화한다.

## 권한 매트릭스

| 주체 | 열람 및 처리 범위 |
| --- | --- |
| 미인증 방문자 | 랜딩, 도입 문의, 유효 링크로 병원 및 프로그램 안내 |
| 환자 | 유효한 연결 범위의 자기 기록, 자기 체크인, 연결 종료 |
| 지정 담당 직원 | 자기 병원에서 배정된 환자의 응답, 조치 및 후속 업무 |
| 의사 | 소속 병원의 환자, 확인·조치 및 후속 업무 |
| 병원 관리자 | 소속 병원 환자, 배정, 직원 권한, 병원 정책·감사, 기간 리포트·CSV |
| 플랫폼 운영자 | 병원 목록, 도입 문의, 운영 집계와 접근 거부 기록. 임상 데이터에는 별도 병원 역할 필요 |
| 데모 | 루프백에서만 사용하는 인메모리 SQLite와 합성 사용자. 운영 연결 및 발송 키 없음 |

정적 화면 경로의 HTML은 열려 있어도 데이터 API가 인증과 테넌트·배정 권한을 다시 확인한다. SMS와 CSV에 대해 운영자 자격만으로는 의료기관 권한을 대체할 수 없다. 초대 만료와 세션 만료는 별도다. 기존 인증은 초대 링크 소지와 수신자 자기 확인이다. 추가 본인 확인 수단의 필요성은 의료기관과 실환자 도입 전에 결정한다.

## 보존·파기·복구

- 병원과 개인정보 담당자가 데이터 항목·목적과 처리 근거, 운영자/병원 역할, 수탁과 국외 처리를 확정한다. 진료 기록과 업무관리 기록의 보존 요건을 각각 검토한다.
- 보존기간 만료 시 삭제 대상과 예외를 식별하고 승인 이력을 남긴다. 환자 본문뿐 아니라 세션, 초대, 업무·분류, 알림, 백업, 내보내기 사본도 검토한다. 현재 보존일수 설정은 기록이며 자동 파기 작업은 없다.
- 암호화 백업과 복원은 합성 SQLite에서 검증 범위가 확인됐다. 호스팅 D1에서 키 보관, 권한, 복구 목표, 복구 리허설과 백업 만료를 운영 전 별도로 확인한다.
- 운영자 오류 로그에는 토큰, 환자 원문, 자유 입력과 비밀키를 남기지 않는지 호스팅 설정까지 점검한다. 소스 검토와 합성 테스트는 운영 설정 검사를 대체하지 않는다.

실시간 응급 확인, 자동 진단, 치료 권고 또는 의료적 안전 판정은 제품 범위에서 제외했다. 기존 업무 분류 규칙의 임상 적합성, 업무 기록과 의료기록의 경계, 처리 근거는 실환자 파일럿 승인 항목이다. [개인정보 보호법](https://www.law.go.kr/법령/개인정보보호법) · [의료법](https://www.law.go.kr/법령/의료법) · [디지털의료제품법](https://www.law.go.kr/법령/디지털의료제품법)
