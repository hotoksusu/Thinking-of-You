# Care 병원 파일럿 운영·개인정보 검토 초안

2026-10-26. 실제 병원 도입 승인서나 법률 적합성 확인서가 아니다. 운영자·병원 담당자·개인정보 및 의료규제 전문가의 검토가 필요하다.

## 서비스 경계와 승인

- 인공관절·척추 수술 후 회복 기록과 병원 업무 확인을 지원한다. 자동 진단·응급 확정·치료 지시를 제공하지 않는다.
- 기본 14일은 검증용 운영 템플릿이다. 병원 관리자는 의료진 검토 근거, 승인 시각, 규칙 버전과 관리기간을 저장한다. 승인 전 자동 분류를 임상 판단에 사용하지 않는다.
- 기존 질문의 의학적 적합성·위험 신호 기준은 병원 승인 대상이며 이번 작업에서 새 의료 규칙을 만들지 않는다. 향후 예측·치료 기능은 식약처 소프트웨어 의료기기 해당성 검토를 별도로 진행한다.
- 저장 완료, 외부 알림 발송, 담당자 확인을 구분한다. 현재 외부 문자·카카오톡 발송은 연동하지 않았다. 담당자가 직접 Work Queue를 확인하고 연락한다. 자동 발송을 기대하는 운영은 시작할 수 없다.

## 병원 온보딩

1. 운영자가 실제 병원 메타데이터를 등록하고 승인된 병원 담당자를 병원 관리자로 지정한다. 플랫폼 운영자는 환자 열람권한을 자동 취득하지 않는다.
2. 병원 관리자가 직원 역할을 부여한다. 간호사·담당 직원은 배정 환자만, 의사는 소속 병원 허용 환자, 병원 관리자는 소속 운영·보고서에 접근한다. 플랫폼 운영자의 환자 접근이 필요하면 병원 관리자가 별도 승인·권한 등록 후 감사기록을 남기고 종료 후 회수한다.
3. 직원 로그인은 Sites의 ChatGPT 인증을 사용한다. 앱은 비밀번호를 저장하지 않는다. 조직 계정 MFA/재인증·세션 정책은 제공 플랫폼 기능을 확인하고 적용해야 한다. 앱에서 MFA 강제를 구현했다고 주장하지 않는다.
4. 퇴사·담당 변경 시 서버 구성원 권한을 회수한다. 다음 API 요청부터 차단된다. 기존 브라우저에 이미 표시된 정보를 원격으로 삭제할 수는 없으므로 공용 PC 잠금과 로그아웃도 적용한다.
5. 실제 환자 수집 근거·민감정보 처리 근거·위탁 계약·안내문을 확인한 뒤 환자를 등록한다. 테스트는 합성 자료만 사용하고 운영 자료를 개발 DB로 복사하지 않는다.
6. 환자 링크는 256비트 난수, 서버 해시 저장, 7일 만료, 재발급 시 기존 링크·세션 폐기. 인증 후 HttpOnly 쿠키로 전환하며 최초 확인·14일 미사용·30일 절대 만료를 적용한다. 링크 공유는 본인정보 접근 위험이 있으므로 전달 대상을 직접 확인한다. 추가 본인확인은 현재 미구현이다.
7. 병원 관리자는 운영 확인시간, 의료진 승인 근거, 보존정책과 관리기간을 확정한다. 병원별 시간은 서버 병원 등록의 운영시간으로 환자에게 표시된다. 운영기준의 확인시간과 병원 안내를 일치시킨다.

## 개인정보 처리방침 확정 체크 항목

처리자 상호·주소·보호책임자·연락처, 환자/대리인 별 처리 근거, 수집 항목·목적·보존기간·파기 절차, 열람·정정·삭제·처리정지 방법, 동의 거부 시 영향, 아동 및 대리인 확인, 위탁·재위탁 업체와 국외 처리 여부·위치·계약, 침해 구제 연락처를 확정한다. 회복 기록 수집과 영업 상담 동의를 분리한다. 단순 연결 확인 체크박스가 적법한 민감정보 동의를 대체한다고 보지 않는다.

건강정보 처리는 [개인정보 보호법 제23조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029927029)의 처리 제한과 안전조치 검토 대상이다. 위탁·안전조치·국외 처리 등 적용 조항은 실제 처리 관계와 계약에 따라 전문가가 검토한다. 임의의 숫자를 법정 보존기간으로 정하지 않는다.

## 병원 계약 초안 항목

- 목적: 승인된 대상자의 퇴원 후 기록·업무관리 파일럿. 체크인 질문·관리기간·담당자·모니터링 시간은 부속 합의서로 지정.
- 개인정보 역할: 병원과 운영자의 처리자/수탁자 관계, 지시 범위, 접근 승인, 재위탁, 국외 처리, 반환·파기·백업 삭제 범위.
- 안전: 실시간 응급 대응 제외, 응급 안내, 미확인 업무 교대·담당자 부재 시 대체 절차, 외부 발송 미연동 고지.
- 운영: 지원 시간, 장애 통보·복구 목표(RTO/RPO는 합의 전 미확정), 로그 열람 승인, 사고 대응·증빙 보존, 계약 종료·이관 절차.
- 비용: Basic 29만/Standard 49만/Pro 79만은 월 가격 가설, Enterprise 상담. 실제 계약가·대상량·직원/부서 범위·세금·지원·해지 조건은 별도 합의. 필수 보안·안전은 요금제 차등 대상 아님.
- 성과: 활성화·7/14일차 참여·처리시간·실측 업무시간을 병원과 공동 검증. 임상성과·절감률 보증 없음.

## 백업·복구·배포 게이트

- 운영 D1의 실제 리소스·플랜·보존·복구 권한을 확인해야 한다. [D1 암호화 문서](https://developers.cloudflare.com/d1/reference/data-security/)와 [Time Travel 문서](https://developers.cloudflare.com/d1/reference/time-travel/)는 공급자 기능 설명이며 이 Site 설정의 검증 증빙이 아니다.
- 승인된 별도 테스트 DB에서 운영 스키마와 같은 복구 리허설을 실시한다. 합성 SQLite의 AES-256-GCM 암호화·무결성·복원 테스트는 자동화했지만 호스팅 D1 복구는 미검증이다.
- `scripts/care-backup.mjs`는 승인된 export 파일을 암호화/복호화하는 오프라인 도구다. `CARE_BACKUP_KEY`는 32바이트 키(64 hex)를 보안 저장소에서 런타임 환경변수로 공급한다. 키를 소스·명령행 인자·로그·백업과 같은 장소에 저장하지 않는다. 출력은 기존 파일을 덮어쓰지 않는다. 평문 export·복원 파일은 승인된 보호 저장소와 접근권한을 사용한다.
- 증분 스키마 `0001_care_operations.sql`만 추가하며 기존 자료를 삭제하지 않는다. DB 복구 bookmark/암호화 export와 마지막 정상 배포를 보존한다. 신규 앱은 새 스키마 적용 후 배포하며, 실패하면 이전 Worker로 롤백하고 추가 테이블을 성급히 삭제하지 않는다.
- 실제 DB 복원은 최신 기록 손실을 초래할 수 있어 사고 지휘자 승인·쓰기 중지·대상 DB 확인·복원 후 건수/무결성/테넌트 권한 검증 없이 실행하지 않는다.

## 일일 운영·사고 대응

개원/교대 시 신규 확인 필요·미처리 Follow-up·미응답·미발송 신호를 확인하고 담당자를 지정한다. 확인·조치·Follow-up 완료는 각각 별도 기록한다. 종료 시 미처리 업무를 인계한다. 자동 알림 장애 감시·재발송 서비스는 미연동이며 사람의 운영 체크를 대체하지 않는다.

사고 의심 시 담당자 접근 회수와 링크 폐기, 영향을 받은 테넌트의 처리 제한, 민감정보 없는 사고 시각/요청 식별자 보존, 범위 조사, 병원·보호책임자 보고, 전문가와 법정 통지 의무·기한 검토, 복구 리허설 후 복원, 사후 권한·원인 검토 순으로 진행한다. 로그에 이름·연락처·증상·본문·원문 토큰을 추가하지 않는다. 플랫폼의 URL 로그에 토큰이 남는지 별도 확인하고 마스킹·접근정책을 합의한다.

## 도입 전 미해결 항목

실제 D1 적용/백업 복원, 신뢰 헤더의 플랫폼 경계·로그 마스킹 확인, MFA/조직 로그인 정책, 추가 환자 본인확인 필요성, 외부 알림 사업자·발송키·실패 재시도·감시, 개인정보·의료규제 계약 검토, 침투 테스트·실기기 접근성, 종료/삭제 요청과 백업 파기 실행 절차가 남아 있다. 호스팅·DB·백업·메시지 비용은 실제 플랜·계약과 사용량으로 견적해야 하며 아직 확인된 운영비가 아니다.
